# 全国花火予定データの取得方針

調査日: 2026-07-26

## 採用方針

- **主データソース: EventBank** — 全国の花火大会候補、日時、地域、会場情報を取得する。
- **補助・照合ソース: JAPAN 47 GO / 日本観光振興協会** — EventBankの候補を照合し、欠落候補の発見と公式URLの補強に使う。
- **最終確認: 主催者・自治体・観光協会の公式発表** — 直近イベント、延期・中止、開始時刻の確定に使う。

この三段階で、単一のまとめサイトや単一ベンダーの欠落・更新遅延に依存しない。

## 結論

「次の花火」を継続して表示する用途では、まとめサイトを直接スクレイピングする方式は採らない。

推奨は、**ライセンス契約した全国イベントDBを候補母集団にし、主催者・自治体・観光協会の公式発表で直近イベントを検証する二層方式**である。アプリには正規化済みの自前JSONだけを配信し、ブラウザから外部サイトや外部APIを直接呼ばない。

理由は三つある。

1. 花火大会は中止・延期・開始時刻変更があり、正確性は件数より重要である。
2. 消費者向けまとめサイトのHTMLは公開API・再配信許諾ではなく、構造変更・権利・アクセス制限のリスクがある。
3. PWAから第三者サービスを直接呼ぶと、APIキー、CORS、オフライン表示、更新失敗時の体験を制御できない。

### 主データ: EventBank

EventBankは花火大会を含む33分類、開催日時・住所・緯度経度・想定動員数などを持ち、全国データをAPI JSONまたはファイルで毎日更新すると案内している。未来データにも対応しているため、「次の花火」表示の候補母集団として適している。[データ概要](https://www.eventbank.jp/lp/data/) [API案内](https://api.eventbank.jp/) [媒体向け詳細](https://www.eventbank.jp/about/view.do?p=media)

ただしAPI配信は法人・団体向けで、アクセスキーと個別条件が必要である。導入前に次を確認する。

- 花火大会カテゴリだけの提供可否と価格
- アプリ画面への表示、キャッシュ、二次配信の可否
- 名称・日時・都道府県・会場座標・公式URL・更新日時の提供可否
- 中止・延期・未定のステータス表現
- レート制限、日次差分、障害時SLA

### 補助・照合: JAPAN 47 GO

日本観光振興協会は都道府県・観光協会・市区町村由来の全国観光DBを提供し、動態イベント情報とAPI仕様書、イベントCSVサンプルを案内している。サイト上では2026年の花火特集も公開されている。商用利用条件とAPI認証・更新頻度は問い合わせで確定させる必要がある。[データ活用案内](https://kankou-data.nihon-kankou-dx.info/) [花火特集・イベントカレンダー](https://www.japan47go.travel/ja)

公開資料では、行・祭事データを開催約3か月前に自治体・観光協会へ更新依頼し、月次更新としている。直前変更の検知には公式確認を重ねる前提が必要である。[全国観光情報DB概要](https://nihon-kankou.or.jp/UserFiles/File/kankou.pdf)

### 照合ルール

EventBankを基準レコードとし、JAPAN 47 GOのイベントを名称・都道府県・市区町村・開催日・会場で候補照合する。

| 状態 | 扱い |
|---|---|
| 両方が日付・地域・大会名で一致 | `confidence: licensed` として採用。公式URLがあれば記録する |
| 日付または開始時刻が異なる | 直近90日以内なら公式発表を確認するまで `provisional` にする |
| EventBankだけに存在 | 候補として保持し、JAPAN 47 GO・公式検索で追認する |
| JAPAN 47 GOだけに存在 | 補完候補として取り込み、EventBankと公式発表で追認する |
| 公式発表が中止・延期を示す | 公式を優先し、`cancelled` または日付更新する |

大会名の表記ゆれだけで重複を生まないよう、正規化した名称、都道府県、市区町村、会場、日付を照合キーにする。自動一致しないレコードは管理キューへ残し、人手で確定する。

### まとめサイトを正本にしない理由

まとめサイトは「候補を探す」には有用でも、転載・再配信・自動取得の許諾はサイトごとに異なる。例えば、じゃらんの公開Webサービスはアカウント登録とAPIキーを要求し、データ利用は非商用目的に限る規約である。花火情報をアプリの恒久データ源にする契約としては適合を個別確認できない限り採用しない。[じゃらんWebサービス利用規約](https://www.jalan.net/jw/jwp0300/jww0301.do)

## 推奨アーキテクチャ

```text
EventBank ──────┐
JAPAN 47 GO ───┼─> 収集ジョブ ─> 正規化・差分照合 ─> 公式確認キュー
自治体オープンデータ ┘                                      │
                                                            自前JSON/API
主催者・自治体・観光協会の公式発表 ────────────────────────────┘
                                                                  │
PWA / Electron / Wallpaper Engine <── オフライン用スナップショット ┘
```

### 1. 収集はサーバー側の定期ジョブに閉じる

- VPS上のcronまたはsystemd timerで毎日実行する。
- APIキーはサーバー環境変数にのみ置く。Viteの`VITE_*`へ入れない。
- 外部応答はそのままクライアントへ流さず、正規化して保存する。
- 配信失敗時は前回正常スナップショットを維持する。

外部SaaSへ実行時依存しない方針を優先するなら、EventBankなどにはAPIではなく日次ファイル（CSV/TSV）を依頼し、VPSの収集ジョブで取り込む。PWAが読むのは常に自前配信のJSONだけにする。これなら外部データ提供元は更新時の入力源に留まり、リアルタイム通信・ユーザーデータ・アプリ表示の可用性を第三者サービスへ委ねない。

### 2. 正規化データを自前で持つ

既存の`HanabiEvent`は表示に必要な最小形を保ち、収集用には別の内部モデルを持つ。

```ts
type EventStatus = 'announced' | 'provisional' | 'cancelled' | 'completed';

interface HanabiEventRecord {
  id: string;                 // 安定した自前ID
  name: string;
  prefecture: string;
  municipality?: string;
  startsAt: string;           // ISO 8601 +09:00
  endsAt?: string;
  venue?: string;
  latitude?: number;
  longitude?: number;
  officialUrl?: string;
  status: EventStatus;
  source: 'eventbank' | 'japan47go' | 'municipality' | 'organizer';
  sourceUrl: string;
  sourceUpdatedAt?: string;
  verifiedAt: string;
  confidence: 'official' | 'licensed' | 'provisional';
}
```

アプリ配信用は、このレコードから必要最小限だけを出す。

```http
GET /api/v1/hanabi/next
GET /api/v1/hanabi/events?from=2026-07-26T00:00:00%2B09:00&to=2026-12-31T23:59:59%2B09:00&prefecture=福岡県
```

`next`は`status=announced`かつ`startsAt > now`を対象にする。開催日未定・中止情報は「次の花火」に混ぜず、管理用キューに残す。

### 3. 公式確認を優先度順に行う

| 時期 | 確認方針 |
|---|---|
| 開催90日超前 | ライセンスDBの候補を表示可。ただし予定・未定を区別する |
| 開催90日前〜7日前 | 公式URLの開催日・時刻を日次確認する |
| 開催7日前〜翌日 | 主催者・自治体・観光協会の公式ページを優先し、変更・中止を即反映する |
| 終了後 | `completed`へ移し、次候補を再計算する |

最初のMVPでは、全国すべてを自動検証しようとせず、画面に表示され得る「直近30件」だけを公式確認キューに入れると運用負荷を抑えられる。

## 段階的な導入案

### Phase A: いま使える最小運用

1. `public/data/hanabi-schedule.json`を自前の編集済みスナップショットとして維持する。
2. 年次更新は、EventBankまたはJAPAN 47 GOへ問い合わせる前に、候補一覧を手動収集する。
3. 直近表示候補だけ公式URLを記録して人手確認する。
4. PWAは現状どおり日程JSONをprecacheし、通信断でも最後に確認済みの予定を表示する。

### Phase B: EventBank + JAPAN 47 GO の二層連携

1. EventBankへ問い合わせ、花火カテゴリだけのAPIまたは日次差分ファイルを見積もる。
2. JAPAN 47 GOの利用条件・API認証・データ提供条件を確認する。
3. 収集ジョブ、重複統合、差分照合、`sourceUrl`・`verifiedAt`の保存を実装する。
4. 自前の`/api/v1/hanabi/next`を配信し、クライアントはそこから日次スナップショットを更新する。
5. 直近イベントについて公式確認の失敗・差分を通知する。

### Phase C: 品質・運用を強化

- 大会名・会場・自治体・日付で重複統合する
- 中止・延期・開催時刻未定を明示する
- 公式URLのリンク切れ、更新停止、日付矛盾を監視する
- 「確認日時」と「情報源」を管理画面または運用ログで追跡する

## 判断と次アクション

### 推奨判断

- 小規模・個人運用: **自前JSON + 直近候補の公式手動確認**
- 継続運用・全国網羅: **EventBankを主データとして契約を問い合わせる**
- 補助・照合: **JAPAN 47 GOの利用条件を確認し、EventBankとの差分検知に使う**
- まとめサイト: **発見と照合に限定し、スクレイピング・転載をデータ供給方式にしない**


## 調査上の注意

- この文書は技術・運用判断のための調査であり、各社データのライセンス解釈を保証するものではない。
- 契約、転載、キャッシュ、商用利用、画像利用は導入前に各提供元の最新規約と書面回答で確認する。
- 主催者公式サイトでも「予定」と「確定」を区別し、取得日時を残す。
